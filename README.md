# CatalogMind

A multi-tenant conversational commerce API — a merchant uploads a product feed and
gets a grounded, streaming shopping assistant scoped strictly to their own catalog.

[![CI](https://github.com/Sky2709/catalogmind/actions/workflows/ci.yml/badge.svg)](https://github.com/Sky2709/catalogmind/actions/workflows/ci.yml)

## Overview

Conversational product discovery is easy to demo and hard to operate: the hard
parts are tenant isolation, catalog heterogeneity, retrieval quality you can
actually measure, and cost per query — not the LLM call itself. CatalogMind is a
FastAPI service that lets a merchant provision an account, upload a CSV product
feed, and immediately query it two ways: a raw hybrid search endpoint, and a
grounded chat agent (Claude via AWS Bedrock, orchestrated with LangGraph) that
answers only from that merchant's own catalog.

What makes it technically interesting: retrieval and generation are kept as
separate concerns (nothing on the search path calls an LLM), the hybrid-search
blend and reranking depth are chosen from measured experiments rather than
guessed, tenant isolation is enforced structurally where the underlying engines
allow it, and the chat agent grounds every answer with a structured marker
protocol instead of pattern-matching its own free-text output. Every number in
this document is regenerated by `make eval` — see [`DECISIONS.md`](DECISIONS.md)
for the reasoning behind each engineering choice.

## Features

- **Multi-tenant catalog ingestion** — CSV feed upload, per-source column mapping
  or adapter, content-hash delta detection (idempotent re-ingestion), background
  job tracking.
- **Hybrid retrieval** — keyword (BM25) + vector search blended via a dynamically
  routed alpha, optional cross-encoder reranking, structured filters (price,
  brand, category, gender, stock, rating).
- **Grounded chat agent** — LangGraph-orchestrated Claude agent with three tools
  (`search_catalog`, `get_catalog_stats`, `get_product_detail`), a
  fast/reasoning model router, a semantic cache, and per-tenant cost tracking.
- **Structural tenant isolation** — Weaviate native multi-tenancy, per-tenant
  MongoDB collections, and single-point tenant resolution from the API key.
- **Measured, not guessed** — a retrieval eval (170 golden queries) and a
  generation eval (218 chat scenarios), both regenerable, back every number
  this project publishes about itself.
- **Observability** — structured per-query trace logs, Prometheus metrics, an
  optional Grafana dashboard, and optional Langfuse LLM tracing.

Retrieval and generation are deliberately separate concerns. Query classification
and alpha selection (`app/retrieval/alpha_router.py`) are pure lexical
heuristics — every search costs microseconds of Python, not a network round
trip. LLM calls exist only in chat generation and in offline, ingestion-time
attribute enrichment.

`app/retrieval/alpha_router.py` and `app/llm/markers.py` are the two files worth
reading first — the lexical query classifier and the grounding protocol are the
project's least conventional pieces.

## Tech stack

| Layer | Choice |
|---|---|
| API | FastAPI + Uvicorn, async throughout, Python 3.12 |
| Vector / hybrid search | Weaviate (native multi-tenancy) |
| Relational store | PostgreSQL + SQLAlchemy (async) + Alembic |
| Raw feed store | MongoDB (one collection per tenant) |
| Cache / rate limiting | Redis |
| Embeddings / reranking | `BAAI/bge-small-en-v1.5`, `BAAI/bge-reranker-base` — local, CPU |
| LLM | Claude (Sonnet 5 / Haiku 4.5) via AWS Bedrock, raw `anthropic[bedrock]` SDK |
| Agent orchestration | LangGraph — scoped to the chat agent only |
| Observability | structlog, Prometheus, Grafana, Langfuse |
| Tooling | uv, ruff, mypy, pytest, Helm (chart lint only) |

## Getting started

### Prerequisites

- Python 3.12 and [`uv`](https://docs.astral.sh/uv/)
- Docker Engine + Compose plugin (Weaviate, Postgres, MongoDB, Redis)
- An AWS Bedrock long-term API key, for the chat agent only — ingestion and
  search work with no external API key

### Installation

```bash
git clone https://github.com/Sky2709/catalogmind.git
cd catalogmind
make install     # Python 3.12 venv + all deps
```

### Configuration

```bash
cp .env.example .env
```

Everything is environment-driven (`app/config.py`); `.env.example` documents the
full surface with safe local defaults. The one value you actually need to set is
`AWS_BEARER_TOKEN_BEDROCK` — without it, ingestion and search still work, but the
chat endpoint will fail.

### Running the project

```bash
make up          # weaviate + postgres + mongo + redis
make migrate      # apply database migrations
make seed         # provision 3 demo merchants, ingest their catalogs
make dev          # http://localhost:8000/docs
```

Swagger UI comes up at `/docs`; a minimal chat page is served at `/ui/` once at
least one catalog is seeded.

## Usage

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/v1/merchants` | Provision a merchant (admin-token gated) |
| `POST` | `/v1/merchants/{tenant}/catalog:ingest` | Upload a CSV feed |
| `POST` | `/v1/merchants/{tenant}/search` | Hybrid keyword + vector search |
| `POST` | `/v1/merchants/{tenant}/chat` | Grounded chat (SSE stream) |
| `GET` | `/v1/merchants/{tenant}/usage` | This merchant's LLM cost |

Full request/response schemas are live at `/docs`. Two examples:

```bash
curl -X POST http://localhost:8000/v1/merchants/demo-fashion-in/search \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"query": "waterproof hiking boots size 10", "filters": {"in_stock_only": true}}'
```

```bash
curl -N -X POST http://localhost:8000/v1/merchants/demo-fashion-in/chat \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"message": "I need waterproof hiking boots, size 10"}'
```

The chat endpoint streams Server-Sent Events (`conversation`, `tool_call`,
`token`, `citations`, `error`) rather than a single JSON response.

## How it works

**Ingestion**: a feed is normalized (messy prices, HTML, encodings) → mapped
onto the internal `Product` model → unchanged rows are skipped via a content
hash → changed rows are embedded locally and upserted into Weaviate with a
deterministic id, so re-running the same feed is idempotent.

**Retrieval**: a query is classified lexically (exploratory / attribute /
identifier, no LLM) → a dynamic alpha is chosen for that class →
Weaviate blends BM25 and vector search → structured filters are applied →
candidates are optionally reranked with a cross-encoder.

**Chat**: a semantic-cache check can short-circuit a repeated question → the
LangGraph agent calls Claude with three tools in a loop, routed between a fast
and a reasoning model tier based on lexical difficulty signals → the answer is
checked against a structured marker protocol (`[[NO_MATCH]]` / `[[SKU:X]]` /
`[[STAT:N]]`) instead of scanned for refusal/citation-shaped prose → the
validated answer, its real citations, and token/cost usage are streamed back
and persisted.

## Testing

```bash
make test       # unit tests only — no external services required
make test-all   # unit + integration — requires `make up` and a real Bedrock key
```

517 unit tests and 54 integration tests, all real (no skips). The most
important one is `tests/integration/test_tenant_isolation.py`: it inserts a
product for one merchant and asserts every possible way of reaching it as
another merchant fails.

## Design decisions

- **Tenant isolation is structural where the engine allows it, disciplined
  where it doesn't** — Weaviate native multi-tenancy and per-tenant Mongo
  collections are structural; Postgres has no row-level security, so isolation
  there depends on every query resolving its tenant through one function
  (`app/deps.py::get_current_merchant`), never from a caller-supplied value.
- **No LLM call on the retrieval hot path** — query classification and alpha
  selection are lexical heuristics, measured against a golden query set rather
  than tuned by hand.
- **A structured marker protocol grounds every generated answer** instead of
  guessing at Claude's free-form prose, after an earlier regex-based approach
  missed a real refusal in production.
- **A pluggable `Retriever` protocol** — one implementation today, designed so
  a second retrieval engine could be scored against the same golden queries
  without touching the chat agent.

Full reasoning and what was tried and rejected: [`DECISIONS.md`](DECISIONS.md).

## Limitations

- No hosted live demo yet — a deployment target (GCP e2-micro VM) is chosen but
  not yet executed; running it yourself is one `make` sequence.
- ~11–12s model warm-up at process startup (embedder + reranker), an accepted
  tradeoff that would need re-solving under a scale-to-zero deployment.
- Conversation history is held in an in-memory LangGraph checkpointer — not
  durable across process restarts.
- The electronics catalog has no structured `brand` field, and its taxonomy is
  missing a "Feature Phones" leaf — known gaps, left open rather than rushed.
- The chat agent handles one tool call per turn; a request needing two
  distinct tools in a single turn isn't yet supported.
